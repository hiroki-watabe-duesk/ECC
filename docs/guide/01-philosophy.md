# 第01章 ハーネスエンジニアリングの思想と原則

ECC の設計がなぜこの形になっているのかを理解する章です。原則を知らずに構成だけ真似ても、新しい状況での判断ができません。ここでは「何を」ではなく「なぜ」に焦点を当て、日々の意思決定に使えるメンタルモデルを構築します。

---

## ハーネスエンジニアリングとは何か

**ハーネスエンジニアリング**とは、Claude Code・Codex・OpenCode・Cursor・Gemini・Zed などの複数の AI エージェントハーネスを横断して一貫動作する、再利用可能・合成可能・永続的なエージェント型ワークフロー層を設計する技芸です。

中心命題は明確です。

> **ECC は再利用可能なワークフロー層。ハーネスは実行面（execution surface）。**

この命題が意味することは、**永続ロジックとハーネス固有アダプタを分離する**ということです。ワークフローの「何を・どんな順序で・どんな基準で」という知識は `skills/`・`rules/`・`hooks/` などのリポジトリ共有ソースに置きます。その知識をどのツールがどう読み込むかという「接続の形」だけをハーネスアダプタが担います。

この分離が崩れると何が起きるか。Claude Code 用に書いたワークフローを Cursor でも動かしたいとき、3 つのハーネス固有コピーを個別にメンテナンスすることになります。`docs/architecture/cross-harness.md` はこれを次の一文で表現しています。

> *If a change requires editing three harness copies of the same workflow, the shared source is in the wrong place.*

3 つのコピーを編集しなければならない状況は、共有ソースの置き場所が間違っているサインです。ワークフローを `skills/` に戻し、ハーネス固有のファイルにはロード・イベント形状・コマンド名のマッピングだけを残してください。

---

## 5 つの中核原則

`SOUL.md` に定義された 5 つの原則は、ECC のすべての設計判断の根拠です。それぞれの「なぜ」と「日々の適用例」を示します。

### 1. Agent-First（エージェントファースト）

**原則**: 仕事はできるだけ早く、適切な専門家エージェントへ委譲する。

**なぜ**: オーケストレータ（メイン Claude）がすべての作業を直接処理すると、コンテキストウィンドウを広く消費し、専門知識を持たない領域でも汎用的な処理をする羽目になります。プランナーは実装戦略に、コードレビュアーは品質に、セキュリティレビュアーは脆弱性発見に特化しています。委譲することで各エージェントは自分のスコープだけを処理し、コンテキストを節約しながら専門的な判断ができます。

**日々の適用例**:
- 複雑な機能を実装する前に `planner` エージェントへ設計を依頼する
- コードを書いた後に自動的に `code-reviewer` を呼ぶ（Stop フックで自動化可能）
- ビルドが壊れたら `build-error-resolver` に投げ、原因調査と修正を委譲する
- セキュリティに関わる変更には必ず `security-reviewer` を通す

### 2. Test-Driven（テスト駆動）

**原則**: 実装を信頼する前にテストを書く、またはリフレッシュする。

**なぜ**: テストなしの変更は後から壊れているかどうかを確認できません。ECC では `tdd-guide` エージェントが「実装前のテスト作成」というサイクルを強制します。また、`tests/` ディレクトリは `scripts/` の構造をミラーし、すべての新しいスクリプトに対応するテストを要求します。この一貫性がリグレッション防止を実用的なコストで維持します。

**日々の適用例**:
- 新しいフックスクリプトを書く前に `tests/hooks/` に統合テストを書く
- `scripts/lib/` に新しいユーティリティを追加する際は `tests/lib/` に対応テストを置く
- コミット前に `node tests/run-all.js` を実行して全テストをパスさせる

### 3. Security-First（セキュリティファースト）

**原則**: 入力を検証し、秘密情報を保護し、安全なデフォルト値を維持する。

**なぜ**: AI エージェントはユーザー入力・外部データ・ツール結果などの多様な入力を処理します。これらはいずれも不正なデータや注入攻撃のベクタになり得ます。CLAUDE.md の「Prompt Defense Baseline」はこの防御を全コンポーネントに適用する基底として機能します。

**日々の適用例**:
- フックスクリプトでは stdin の JSON パースが失敗しても `exit 0` し、ツール実行をブロックしない
- スキルや設定ファイルに API キー・トークン・パスワードを一切書かない
- 外部から取得したデータ（MCP の返却値、URL のコンテンツ）は信頼できないコンテンツとして扱う
- `[HookName]` プレフィックスをつけてエラーを stderr へ記録し、デバッグを容易にする

### 4. Immutability（不変性）

**原則**: 既存状態を変更するより、明示的な状態遷移を優先する。

**なぜ**: 変更可能な状態は追跡が難しく、バグの温床になります。ECC では設定変更をマニフェストと状態ストア（`schemas/install-state.schema.json` に定義）で管理し、何がいつインストールされたかを記録します。スキルの進化は上書きではなく新バージョンとして追跡されます。

**日々の適用例**:
- インストール状態は `node scripts/ecc.js list-installed` で確認し、手動で直接ファイルを消さない
- フックの変更はセマンティックフォールバックエイリアス付きの安定 ID で管理する
- 設定の破壊的変更は PR レビューで検証する（`WORKING-CONTEXT.md` の制約に従う）

### 5. Plan Before Execute（実行前に計画する）

**原則**: 複雑な変更は段階に分割してから実行する。

**なぜ**: 計画なしに複雑な変更を開始すると、中途半端な状態で詰まったとき、どこまで進んでいて何が残っているかが不明になります。`planner` エージェントと `/plan` コマンドは、実装前の計画フェーズをファーストクラスのワークフローとして位置づけます。

**日々の適用例**:
- 5 ファイル以上にまたがる変更は `/plan` で事前に段階を定義する
- 複雑なリファクタリングは `planner` エージェントに依頼し、フェーズ分割案を作成させる
- 計画はコミット可能なドキュメントとして残し、途中再開の基準点にする

## スキルファースト移行

ECC は現在、**コマンドからスキルへ**の移行期にあります。`WORKING-CONTEXT.md` はこれを明確に定義しています。

> *move repo guidance and contribution flow to skills-first, leaving commands only as explicit compatibility shims*

`commands/` 配下のスラッシュコマンドは、ユーザーが既存のワークフローを壊さずに移行できるようにするための**互換シム**です。永続ロジックは `skills/` に置きます。

この移行の理由は実用的です。スキルは Claude Code プラグイン・Codex・OpenCode・Cursor など複数のハーネスに同じソースからインストールできますが、コマンドはハーネスのスラッシュコマンド実装に依存するため可搬性が低いのです。スキルに書かれたワークフローは「指示・構造・ワークフロー形状」であり、ほぼすべてのハーネスが読める形式です。

**実践への落とし込み**:
- 新しいワークフローは最初から `skills/` に書く
- `/tdd` などの既存コマンドは残すが、ロジックを追加・修正する場合は `skills/tdd-workflow/SKILL.md` 側に書く
- 自分のプロジェクトに ECC パターンを持ち込む際は、コマンドではなくスキルをコピーする

## 再利用ワークフローの複利効果

`the-longform-guide.md` には実践から得られた格言が記録されています。

> *"Early on, I spent time building reusable workflows/patterns. Tedious to build, but this had a wild compounding effect as models and agent harnesses improved."*（@omarsar0）

この「複利的な効果」は具体的に何を意味するか。

一度 `tdd-workflow` スキルを正しく書けば、すべてのプロジェクトで同じ品質の TDD サイクルが再現されます。AI モデルが改善されれば、スキルの説明文はそのままで動作品質が上がります。新しいハーネスが登場すれば、スキルをそのハーネスのインストールパスに追加するだけで対応できます。

反対に、プロジェクトごとに CLAUDE.md に手順を書き直すアプローチは、複利ではなく単純コストの積み上げです。チームが増えるほど、ハーネスが増えるほど、メンテナンスコストは線形に増加します。

**最小限の並列化で最大の成果を得る**という考え方も同じ文脈です（`the-longform-guide.md`）。並列 Claude インスタンスを闇雲に増やすのではなく、「本当に必要なときだけ追加する」という規律が生産性を高めます。スコープが明確な委譲と、再利用可能なスキルがあれば、少ないインスタンスでより多くの成果を出せます。

---

## まとめ: 判断の基準として使う

5 原則とスキルファースト移行は、「これは正しい実装か」を問うための判断基準です。新しいワークフローを追加するとき、次の問いを立ててください。

1. これは特定ハーネスにしか動かないロジックを含んでいるか？ → `skills/` に移動して共有ソースにする
2. このワークフローに対応するテストがあるか？ → Test-Driven 原則を適用する
3. 外部入力を信頼せずに処理しているか？ → Security-First 原則を確認する
4. 変更前に計画フェーズを踏んだか？ → Plan Before Execute を確認する
5. 適切な専門エージェントに委譲しているか？ → Agent-First 原則を適用する
