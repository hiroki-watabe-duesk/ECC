ある問題、CVE-2025-59536（CVSS 8.7）は、ユーザーが信頼ダイアログを承認する前に、プロジェクトに含まれたコードの実行を許してしまうものでした。別の問題、CVE-2026-21852 は、攻撃者が制御する `ANTHROPIC_BASE_URL` を通じてAPIトラフィックを迂回させ、信頼が確認される前にAPIキーを漏洩させることを許しました。必要だったのは、リポジトリをクローンしてツールを開く、ただそれだけです。

私たちが信頼するツールは、同時に標的にされているツールでもあります。これが転換点です。プロンプトインジェクションはもはや、間の抜けたモデルの失敗や、おもしろいジェイルブレイクのスクリーンショット（とはいえ後ほど面白いものを一つ紹介します）ではありません。エージェントシステムにおいては、それはシェル実行、シークレットの露出、ワークフローの悪用、あるいは静かな横方向移動（lateral movement）になりえます。

# 攻撃ベクトル / 攻撃面

攻撃ベクトルとは、本質的に、やり取りのあらゆる入口（エントリーポイント）です。エージェントが接続しているサービスが多いほど、抱えるリスクは大きくなります。エージェントに与えられる外部情報は、リスクを高めます。

例: 私のエージェントはゲートウェイ層を介して WhatsApp に接続しています。攻撃者はあなたの WhatsApp 番号を知っています。彼らは既存のジェイルブレイクを使ってプロンプトインジェクションを試みます。チャットにジェイルブレイクを連投します。エージェントはそのメッセージを読み、指示として受け取ります。そして私的な情報を明かす応答を実行します。もしあなたのエージェントがroot権限、または広範なファイルシステムアクセス、あるいは有用な認証情報をロードしているなら、あなたは侵害されています。

人々が笑うこの「Good Rudi」ジェイルブレイクのクリップでさえ（正直おもしろい）、同じ種類の問題を指しています。繰り返しの試行、最終的に機微情報の暴露、表面上はユーモラスでも、根底にある失敗は深刻です —— だってあれは子供向けのものなのですから。ここから少し外挿すれば、なぜこれが破滅的になりうるのか、すぐに結論にたどり着くでしょう。モデルが実際のツールと実際の権限に接続されているとき、同じパターンはずっと先まで及びます。

WhatsApp は一例にすぎません。メールの添付ファイルは巨大なベクトルです。攻撃者がプロンプトを埋め込んだPDFを送り、エージェントは仕事の一環として添付を読み、本来は有用なデータに留まるべきだったテキストが、悪意ある指示に変わってしまいます。スクリーンショットやスキャンも、OCRをかけているなら同じくらい危険です。Anthropic自身のプロンプトインジェクション研究も、隠しテキストや改変された画像を本物の攻撃材料として明確に指摘しています。

GitHubのPRレビューも、もう一つの標的です。悪意ある指示は、隠されたdiffコメント、issue本文、リンクされたドキュメント、ツール出力、さらには「役立つ」レビューコンテキストの中に潜みえます。上流にボット（コードレビューエージェント、Greptile、Cubic など）を設定していたり、下流でローカルの自動化手法（OpenClaw、Claude Code、Codex、Copilot coding agent、何であれ）を使っていたりして、低い監督と高い自律性でPRをレビューしているなら、あなたはプロンプトインジェクションを受けるリスクの攻撃面を増やしている「うえに」、そのエクスプロイトであなたのリポジトリの下流にいるすべてのユーザーに影響を及ぼしています。

GitHub自身のコーディングエージェント設計は、その脅威モデルを静かに認めたものです。書き込み権限を持つユーザーだけがエージェントに作業を割り当てられます。より低い権限のコメントはエージェントに見せられません。隠し文字はフィルタされます。プッシュは制約されます。ワークフローは依然として人間が **Approve and run workflows** をクリックすることを必要とします。彼らがそうした予防策を取りつつあなたの手を引いていて、あなたがそれに気づきすらしていないのなら、自分でサービスを管理・ホストするときに何が起きるでしょうか?

MCPサーバーは、まったく別の層です。偶然に脆弱なこともあれば、設計上悪意あることも、あるいは単にクライアントから過度に信頼されていることもあります。ツールは、コンテキストを提供する、あるいは本来返すべき情報を返すように見せかけながら、データを抜き取ることができます。OWASP がまさにこの理由で MCP Top 10 を持つようになりました —— ツールポイズニング、コンテキストペイロードを介したプロンプトインジェクション、コマンドインジェクション、シャドウMCPサーバー、シークレットの露出。あなたのモデルがツールの説明・スキーマ・ツール出力を信頼できるコンテキストとして扱うようになった時点で、ツールチェーンそのものがあなたの攻撃面の一部になります。

ここでネットワーク効果がどれほど深くまで及びうるか、見え始めてきたはずです。攻撃面のリスクが高く、チェーンの一つのリンクが感染すると、その下のリンクを汚染します。エージェントは複数の信頼経路の真ん中に同時に座っているため、脆弱性は感染症のように広がります。

Simon Willison の「致死の三要素（lethal trifecta）」という枠組みは、いまだにこれを考える最もすっきりした方法です —— 私的データ、信頼できないコンテンツ、外部通信。この3つすべてが同じランタイムに同居した時点で、プロンプトインジェクションは面白いものではなくなり、データの抜き取りになり始めます。

## Claude Code の CVE（2026年2月）

Check Point Research は2026年2月25日にClaude Codeの調査結果を公表しました。これらの問題は2025年7月から12月の間に報告され、公表前にパッチが当てられました。

重要なのは、CVE IDや事後検証（postmortem）だけではありません。それは、私たちのハーネスの実行層で実際に何が起きているのかを明らかにしてくれます。

CVE-2025-59536。信頼ダイアログが承認される前に、プロジェクトに含まれたコードが実行されうるものでした。NVD と GitHub の勧告（advisory）はともに、これを `1.0.111` より前のバージョンに結びつけています。

CVE-2026-21852。攻撃者が制御するプロジェクトが `ANTHROPIC_BASE_URL` を上書きし、APIトラフィックを迂回させ、信頼確認の前にAPIキーを漏洩させられるものでした。NVD によれば、手動更新者は `2.0.65` 以降であるべきです。

MCP同意の悪用。Check Point はまた、リポジトリが制御するMCP設定と各種設定が、ユーザーがそのディレクトリを意味のある形で信頼する前に、プロジェクトのMCPサーバーを自動承認しうることも示しました。

プロジェクト設定、フック、MCP設定、環境変数が、今や実行面（execution surface）の一部であることが明らかです。

Anthropic自身のドキュメントもその現実を反映しています。プロジェクト設定は `.claude/` にあります。プロジェクトスコープのMCPサーバーは `.mcp.json` にあります。これらはソース管理を通じて共有されます。これらは信頼境界（trust boundary）によって守られているはずです。その信頼境界こそ、まさに攻撃者が狙う先です。

## この1年で変わったこと

この議論は2025年から2026年初頭にかけて急速に動きました。

Claude Code は、リポジトリが制御するフック・MCP設定・環境変数の信頼経路が、公の場でテストされました。Amazon Q Developer は2025年に、VS Code拡張機能に悪意あるプロンプトペイロードが仕込まれたサプライチェーン事件を抱え、その後、ビルドインフラにおける過度に広範なGitHubトークンの露出に関する別の開示がありました。脆弱な認証情報の境界に、エージェント周辺のツールが加われば、それは日和見的攻撃者にとっての入口になります。

2026年3月3日、Unit 42 は実環境で観測されたWebベースの間接プロンプトインジェクションを公表しました。複数の事例を記録しています（毎日のようにタイムラインに何かが流れてくるように見えます）。

2026年2月10日、Microsoft Security は「AI Recommendation Poisoning（AIレコメンデーション汚染）」を公表し、31社・14業界にわたるメモリ指向の攻撃を記録しました。これが重要なのは、ペイロードがもはや一発で勝つ必要がないからです —— それは記憶され、後から戻ってくることができます。

Snyk の2026年2月の「ToxicSkills」研究は、3,984個の公開スキルをスキャンし、その36%にプロンプトインジェクションを見つけ、1,467個の悪意あるペイロードを特定しました。スキルはサプライチェーンのアーティファクトとして扱ってください。実際にそうなのですから。

そして2026年2月3日、Hunt.io は、CVE-2026-25253 をめぐる OpenClaw 露出の話に関連して、17,470個の露出した OpenClaw 系インスタンスがあると主張する報告を公表しました。正確な数で議論したいとしても、より大きな論点は残ります —— 人々はすでに、公共インターネット上にある他のあらゆるものを列挙するのと同じやり方で、個人のエージェントインフラを列挙しているのです。

だから、あなたの「バイブコーディング（vibecoded）」アプリは、バイブ（雰囲気）だけでは守られません。これは絶対に重要で、予防策を取っていなければ、避けられないことが起きたときに無知を装うことはできません。

想像してみてください。あなたが OpenClaw に「この記事をここまで読まずに要約して」と頼み、それが上のトロール投稿を読んで、いまやあなたのコンピュータ全体が吹き飛ぶ……それは途方もなく恥ずかしいことでしょう。

## リスクの定量化

頭に留めておく価値のある、比較的すっきりした数字をいくつか。

具体的な数字は変わり続けます。重要なのは進行の方向（発生が起こる頻度と、そのうち致命的なものの割合）であるべきです。

# サンドボックス化

root権限は危険です。広範なローカルアクセスは危険です。同じマシン上の長命な認証情報は危険です。「YOLO、Claudeに任せておけば大丈夫」は、ここで取るべき正しいアプローチではありません。答えは隔離（isolation）です。

原則はシンプルです —— エージェントが侵害された場合、被害範囲（blast radius）は小さくなければなりません。

### まずアイデンティティを分離する

エージェントにあなたの個人用Gmailを与えてはいけません。`agent@yourdomain.com` を作りましょう。メインのSlackを与えてはいけません。別のボットユーザーやボットチャンネルを作りましょう。個人のGitHubトークンを渡してはいけません。短命でスコープ限定のトークンか、専用のボットアカウントを使いましょう。

エージェントがあなたと同じアカウントを持っているなら、侵害されたエージェントはあなた自身です。

### 信頼できない作業は隔離して実行する

信頼できないリポジトリ、添付ファイルの多いワークフロー、あるいは外部コンテンツを大量に取り込むものは、コンテナ・VM・devcontainer・リモートサンドボックスで実行しましょう。Anthropic は、より強固な隔離のためにコンテナ／devcontainer を明確に推奨しています。OpenAI の Codex ガイダンスも、タスクごとのサンドボックスと明示的なネットワーク承認で、同じ方向を後押ししています。業界がこれに収束しているのには理由があります。

Docker Compose や devcontainer を使って、デフォルトでは外向き通信（egress）のないプライベートネットワークを作りましょう。

`internal: true` が重要です。エージェントが侵害されても、あなたが意図的に外への経路を与えない限り、エージェントは「電話して情報を送る（phone home）」ことができません。

一度きりのリポジトリレビューでも、素のコンテナの方がホストマシンよりましです。

ネットワークなし。`/workspace` の外へのアクセスなし。はるかに良い失敗モードです。

### ツールとパスを制限する

これは人々が飛ばす退屈な部分です。同時に、最も効果の高い統制の一つでもあります —— とても簡単に実行できるので、文字どおりROIが振り切れています。

ハーネスがツール権限をサポートしているなら、明らかに機微な対象を中心とした拒否（deny）ルールから始めましょう。

これは完全なポリシーではありません —— が、身を守るためのかなり堅実なベースラインです。

ワークフローがリポジトリを読んでテストを走らせるだけでよいなら、ホームディレクトリを読ませてはいけません。単一のリポジトリトークンだけが必要なら、組織全体の書き込み権限を渡してはいけません。本番（production）が不要なら、本番から遠ざけておきましょう。

# サニタイズ（無害化）

LLMが読むものはすべて実行可能なコンテキストです。テキストがコンテキストウィンドウに入った時点で、「データ」と「指示」の間に意味のある区別はありません。サニタイズは見栄えのためのものではなく、ランタイム境界の一部です。

### 隠しUnicodeとコメントペイロード

不可視のUnicode文字は、攻撃者にとって容易な勝ち筋です。人間は見落とし、モデルは見落とさないからです。ゼロ幅スペース、ワードジョイナー、bidi上書き文字、HTMLコメント、埋め込まれたbase64 —— そのすべてをチェックする必要があります。

安価な一次スキャン:

スキル、フック、ルール、プロンプトファイルをレビューしているなら、広範な権限変更や外向きコマンドもチェックしましょう。

### モデルが見る前に添付ファイルをサニタイズする

PDF、スクリーンショット、DOCXファイル、HTMLを処理するなら、まず隔離（quarantine）しましょう。

実践的なルール:

1. 必要なテキストだけを抽出する

1. 可能な限りコメントとメタデータを取り除く

1. 生きた外部リンクを、特権を持つエージェントに直接与えない

1. タスクが事実の抽出なら、抽出ステップを、行動を取るエージェントから分離する

この分離が重要です。あるエージェントは制限された環境でドキュメントを解析できます。より強い承認を持つ別のエージェントは、クリーンになった要約に対してのみ行動できます。同じワークフローでも、はるかに安全です。

### リンク先のコンテンツもサニタイズする

外部ドキュメントを指すスキルやルールは、サプライチェーン上の負債です。リンクがあなたの承認なしに変わりうるなら、それは後にインジェクションの発生源になりえます。

コンテンツをインライン化できるなら、インライン化しましょう。できないなら、リンクのそばにガードレールを添えましょう。

完璧（bulletproof）ではありません。それでもやる価値はあります。

# 承認境界 / 最小エージェンシー（Least Agency）

モデルは、シェル実行、ネットワーク呼び出し、ワークスペース外への書き込み、シークレットの読み取り、ワークフロー起動について、最終的な権限者であってはなりません。

ここで多くの人がいまだに混乱します。安全境界はシステムプロンプトだと思っているのです。違います。安全境界は、モデルと行動の「あいだ」に位置するポリシーです。

GitHub のコーディングエージェント設定は、ここで良い実践的テンプレートになります。

- 書き込み権限を持つユーザーだけがエージェントに作業を割り当てられる

- より低い権限のコメントは除外される

- エージェントのプッシュは制約される

- インターネットアクセスはファイアウォールの許可リストで制限できる

- ワークフローは依然として人間の承認を必要とする

これが正しいモデルです。

ローカルでも真似しましょう。

- サンドボックス外のシェルコマンドの前に承認を要求する

- ネットワークの外向き通信の前に承認を要求する

- シークレットを含むパスの読み取りの前に承認を要求する

- リポジトリ外への書き込みの前に承認を要求する

- ワークフロー起動やデプロイの前に承認を要求する

ワークフローがそれらすべて（あるいはそのうちの一つでも）を自動承認しているなら、あなたは自律性（autonomy）を持っていません。自分のブレーキ線を切って、うまくいくことを祈っているのです —— 交通量がなく、道路の段差もなく、安全に止まれるだろう、と。

OWASP の「最小権限（least privilege）」をめぐる言い回しは、エージェントにきれいに対応しますが、私はそれを「最小エージェンシー（least agency）」と考える方を好みます。タスクが実際に必要とする、最小限の動ける余地だけをエージェントに与えましょう。

# 可観測性 / ロギング

エージェントが何を読み、どのツールを呼び、どのネットワーク宛先に到達しようとしたかが見えないなら、それを守ることはできません（これは当たり前のはずですが、ralphループで `claude --dangerously-skip-permissions` を叩いて、何の心配もなく立ち去る人たちを見かけます）。そして戻ってくると、ぐちゃぐちゃのコードベースが待っていて、作業を進めるより、エージェントが何をしたのかを解明するのに多くの時間を費やすことになります。

少なくとも次のものをログしましょう。

- ツール名

- 入力の要約

- 触れたファイル

- 承認の判断

- ネットワークの試行

- セッション / タスクID

構造化ログがあれば、始めるには十分です。

何らかの規模でこれを運用しているなら、OpenTelemetry あるいは同等のものに接続しましょう。重要なのは特定のベンダーではなく、異常なツール呼び出しが際立つように、セッションのベースラインを持つことです。

Unit 42 の間接プロンプトインジェクションに関する研究と、OpenAI の最新ガイダンスは、ともに同じ方向を指しています —— 一部の悪意あるコンテンツは通り抜けると想定し、そのうえで次に起こることを制約せよ、と。

# キルスイッチ

graceful（優雅な）killと hard（強制）killの違いを知りましょう。`SIGTERM` はプロセスにクリーンアップの機会を与えます。`SIGKILL` は即座に停止させます。どちらも重要です。

また、親だけでなくプロセスグループ全体をkillしましょう。親だけをkillすると、子プロセスは動き続けることができます。（これはまた、朝に Ghostty のタブを見ると、64GBしかないコンピュータでなぜか100GBのRAMを消費していて、プロセスは一時停止しているのに、シャットダウンしたと思っていた多数の子プロセスが暴走している、ということが時々起こる理由でもあります）

Node の例:

無人ループには、ハートビート（heartbeat）を加えましょう。エージェントが30秒ごとにチェックインしなくなったら、自動的にkillします。侵害されたプロセスが礼儀正しく自分で止まることを当てにしてはいけません。

実践的なデッドマンスイッチ:

- スーパーバイザーがタスクを開始する

- タスクは30秒ごとにハートビートを書き込む

- ハートビートが止まったら、スーパーバイザーがプロセスグループをkillする

- 止まったタスクはログレビューのために隔離される

本物の停止経路を持っていないなら、あなたの「自律システム」は、まさにあなたが制御を取り戻す必要があるその瞬間に、あなたを無視しうるのです。（OpenClaw でこれを見ました。`/stop`、`/kill` などが効かず、暴走するエージェントに対して人々は何もできませんでした）人々は OpenClaw での失敗を投稿したMetaのあの女性をズタズタに引き裂きましたが、それはまさに、なぜこれが必要なのかを示しています。

# メモリ

永続的なメモリは有用です。それは同時にガソリンでもあります。

でも、たいていその部分を忘れますよね? だって、長く使っている知識ベースの中にすでにある .md ファイルを、誰が常時チェックしているでしょうか。ペイロードは一発で勝つ必要はありません。断片を植え付け、待ち、後で組み立てることができます。Microsoft の「AIレコメンデーション汚染」報告は、それを最も明確に思い出させてくれる最近の例です。

Anthropic は、Claude Code がセッション開始時にメモリをロードすると文書化しています。だからメモリは狭く保ちましょう。

- シークレットをメモリファイルに保存しない

- プロジェクトメモリをユーザーグローバルメモリから分離する

- 信頼できない実行のあとはメモリをリセットまたはローテーションする

- 高リスクのワークフローでは長命なメモリを完全に無効化する

ワークフローが一日中、外部ドキュメント・メールの添付・インターネットのコンテンツに触れているなら、それに長命の共有メモリを与えることは、永続化（persistence）を容易にしているだけです。

## 最低ライン・チェックリスト

2026年にエージェントを自律的に運用しているなら、これが最低ラインです。

- エージェントのアイデンティティを個人アカウントから分離する

- 短命でスコープ限定の認証情報を使う

- 信頼できない作業をコンテナ・devcontainer・VM・リモートサンドボックスで実行する

- 外向きネットワークをデフォルトで拒否する

- シークレットを含むパスからの読み取りを制限する

- 特権を持つエージェントが見る前に、ファイル・HTML・スクリーンショット・リンク先コンテンツをサニタイズする

- サンドボックス外のシェル、外向き通信、デプロイ、リポジトリ外への書き込みに承認を要求する

- ツール呼び出し・承認・ネットワーク試行をログする

- プロセスグループのkillと、ハートビートベースのデッドマンスイッチを実装する

- 永続的なメモリを狭く、使い捨て可能に保つ

- スキル・フック・MCP設定・エージェント記述子（descriptor）を、他のあらゆるサプライチェーンのアーティファクトと同様にスキャンする

これをやれと「提案」しているのではありません —— やれと「言っている」のです。あなたのため、私のため、そしてあなたの未来の顧客のために。

## ツールのランドスケープ

良い知らせは、エコシステムが追いついてきていることです。十分速くはありませんが、動いています。

Anthropic は Claude Code を堅牢化（harden）し、信頼・権限・MCP・メモリ・フック・隔離環境をめぐる具体的なセキュリティガイダンスを公表しました。

GitHub は、リポジトリのポイズニングと権限の悪用が現実であると明確に想定した、コーディングエージェントの統制を構築しました。

OpenAI も今や、口に出しにくいことをはっきり言うようになりました —— プロンプトインジェクションは、プロンプト設計の問題ではなく、システム設計の問題である、と。

OWASP には MCP Top 10 があります。まだ進行中のプロジェクトですが、エコシステムがそれを必要とするほど危険になったからこそ、いまそのカテゴリが存在するのです。

Snyk の `agent-scan` と関連の取り組みは、MCP / スキルのレビューに有用です。

そして、特に ECC を使っているなら、これもまさに私が AgentShield を作った問題領域です —— 疑わしいフック、隠れたプロンプトインジェクションのパターン、過度に広範な権限、リスクのあるMCP設定、シークレットの露出、そして手動レビューで人々が必ず見落とすもの。

攻撃面は広がっています。それに対抗するツールは改善しています。しかし、「バイブコーディング」空間における、基本的なオプセック（opsec）／コグセック（cogsec）への犯罪的なまでの無関心は、いまだに間違っています。

人々はいまだにこう考えています。

- 「悪いプロンプト」を打ち込まなければならない

- 直し方は「より良い指示、簡単なセキュリティチェックを走らせ、他に何も確認せず main に直接プッシュする」ことだ

- エクスプロイトには、劇的なジェイルブレイクや何らかのエッジケースが必要だ

だからこそ、エージェントセキュリティはインフラとして扱われなければなりません。

後付けや、雰囲気や、語るのは好きでも誰も何もしないもの、としてではなく —— 必須のインフラとして。

エージェントを自律的に運用しているなら、もはや問いは「プロンプトインジェクションが存在するかどうか」ではありません。存在します。問いは、「あなたのランタイムが、価値あるものを保持しながら、モデルがいつか敵対的な何かを読むことを想定しているかどうか」です。
