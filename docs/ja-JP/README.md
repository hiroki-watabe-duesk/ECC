単なる設定ファイルの集合ではありません。スキル、インスティンクト、メモリ最適化、継続的学習、セキュリティスキャン、リサーチファースト開発を備えた完全なシステムです。実際のプロダクトを構築する10ヶ月以上の集中的な日常使用を通じて進化した、プロダクション対応のエージェント、スキル、フック、ルール、MCP設定、およびレガシーコマンドシムを提供します。

**Codex**、**Claude Code**、**Cursor**、**OpenCode**、**Gemini**、**Zed**、**GitHub Copilot**、その他のAIエージェントハーネス全体で動作します。

ECC v2.0.0-rc.1 では、その再利用可能なレイヤーの上にパブリックHermesオペレーターストーリーが追加されます。まず [Hermesセットアップガイド](docs/HERMES-SETUP.md) を確認し、次に [rc.1リリースノート](docs/releases/2.0.0-rc.1/release-notes.md) と [クロスハーネスアーキテクチャ](docs/architecture/cross-harness.md) を参照してください。

### インストールパスを1つだけ選ぶ

Claude Code のほとんどのユーザーは、インストールパスを1つだけ使用してください:

- **推奨デフォルト:** Claude Code プラグインをインストールし、実際に必要なルールフォルダのみをコピーする。
- **手動インストーラーを使用するのは:** より細かい制御が必要な場合、プラグインパスを完全に回避したい場合、またはセルフホスト型マーケットプレイスエントリの解決に Claude Code ビルドが問題を抱えている場合のみ。
- **インストール方法を重ねて使わないこと。** 最も多い壊れたセットアップは: 最初に `/plugin install` を実行し、その後に `install.sh --profile full` または `npx ecc-install --profile full` を実行するケースです。

すでに複数のインストールを重ねて内容が重複しているように見える場合は、直接 [ECC のリセット / アンインストール](#reset--uninstall-ecc) にスキップしてください。

### ローコンテキスト / フックなしパス

フックがグローバルすぎると感じる場合や、ECC のルール、エージェント、コマンド、コアワークフロースキルのみが必要な場合は、プラグインをスキップして最小限の手動プロファイルを使用してください:

```bash
./install.sh --profile minimal --target claude
```

```powershell
.\install.ps1 --profile minimal --target claude
# or
npx ecc-install --profile minimal --target claude
```

このプロファイルは意図的に `hooks-runtime` を除外しています。

通常のコアプロファイルが必要だがフックをオフにしたい場合は、以下を使用してください:

```bash
./install.sh --profile core --without baseline:hooks --target claude
```

ランタイム強制が必要になった場合にのみ、後からフックを追加してください:

```bash
./install.sh --target claude --modules hooks-runtime
```

### まず適切なコンポーネントを見つける

### 名前付け + 移行に関する注意

ECC には現在3つのパブリック識別子があり、それらは互換性がありません:

- GitHub ソースリポジトリ: `affaan-m/ECC`
- Claude マーケットプレイス / プラグイン識別子: `ecc@ecc`
- npm パッケージ: `ecc-universal`

これは意図的なものです。Anthropic マーケットプレイス / プラグインのインストールは正規プラグイン識別子をキーとするため、ECC は `ecc@ecc` を使用してツール名とスラッシュコマンドの名前空間を Desktop/API の厳格なバリデーターに対応できる長さに保っています。古い投稿では以前の長いマーケットプレイス識別子が表示されていることがありますが、それはレガシーエイリアスとしてのみ扱ってください。また、npm パッケージは `ecc-universal` のままであるため、npm インストールとマーケットプレイスインストールは意図的に異なる名前を使用しています。

### ステップ 2: 必要な場合のみルールをインストールする

> 警告: **重要:** Claude Code プラグインは `rules` を自動的に配布できません。
>
> すでに `/plugin install` で ECC をインストールしている場合は、**その後に `./install.sh --profile full`、`.\install.ps1 --profile full`、または `npx ecc-install --profile full` を実行しないでください**。プラグインはすでに ECC のスキル、コマンド、フックをロードしています。プラグインインストール後にフルインストーラーを実行すると、同じサーフェスがユーザーディレクトリにコピーされ、スキルとランタイム動作が重複する可能性があります。
>
> プラグインインストールの場合は、必要な `rules/` ディレクトリのみを `~/.claude/rules/ecc/` 以下に手動でコピーしてください。まず `rules/common` と、実際に使用する1つの言語またはフレームワークパックから始めてください。すべてのルールディレクトリをコピーするのは、そのコンテキストをすべて Claude に含めることを明示的に望む場合のみにしてください。
>
> フルインストーラーは、プラグインパスの代わりに完全に手動で ECC をインストールする場合のみ使用してください。
>
> ローカルの Claude セットアップが消去またはリセットされた場合でも、ECC を再購入する必要はありません。まず `node scripts/ecc.js list-installed` を実行し、次に `node scripts/ecc.js doctor` と `node scripts/ecc.js repair` を実行してから、何かを再インストールしてください。これにより、通常はセットアップを再構築せずに ECC 管理ファイルが復元されます。問題が ECC Tools のアカウントまたはマーケットプレイスアクセスに関するものであれば、請求 / アカウント回復を別途対処してください。

```bash
# Clone the repo first
git clone https://github.com/affaan-m/ECC.git
cd ECC

# Install dependencies (pick your package manager)
npm install        # or: pnpm install | yarn install | bun install

# Plugin install path: copy only ECC rules into an ECC-owned namespace
mkdir -p ~/.claude/rules/ecc
cp -R rules/common ~/.claude/rules/ecc/
cp -R rules/typescript ~/.claude/rules/ecc/

# Fully manual ECC install path (use this instead of /plugin install)
# ./install.sh --profile full
```

```powershell
# Windows PowerShell

# Plugin install path: copy only ECC rules into an ECC-owned namespace
New-Item -ItemType Directory -Force -Path "$HOME/.claude/rules/ecc" | Out-Null
Copy-Item -Recurse rules/common "$HOME/.claude/rules/ecc/"
Copy-Item -Recurse rules/typescript "$HOME/.claude/rules/ecc/"

# Fully manual ECC install path (use this instead of /plugin install)
# .\install.ps1 --profile full
# npx ecc-install --profile full
```

手動インストールの手順については `rules/` フォルダ内の README を参照してください。ルールを手動でコピーする場合は、フォルダ内のファイルではなく言語ディレクトリ全体（例: `rules/common` または `rules/golang`）をコピーしてください。これにより、相対参照が機能し続け、ファイル名の衝突が発生しません。

### ECC のリセット / アンインストール

ECC が重複、過干渉、または壊れていると感じる場合は、その上にインストールを重ねないでください。

- **プラグインパス:** Claude Code からプラグインを削除し、`~/.claude/rules/ecc/` 以下に手動でコピーした特定のルールフォルダを削除してください。
- **手動インストーラー / CLI パス:** リポジトリルートから、まず削除のプレビューを確認してください:

```bash
node scripts/uninstall.js --dry-run
```

次に ECC 管理ファイルを削除してください:

```bash
node scripts/uninstall.js
```

ライフサイクルラッパーを使用することもできます:

```bash
node scripts/ecc.js list-installed
node scripts/ecc.js doctor
node scripts/ecc.js repair
node scripts/ecc.js uninstall --dry-run
```

ECC はインストール状態に記録されたファイルのみを削除します。インストールしていない無関係なファイルは削除しません。

複数の方法を重ねた場合は、次の順序でクリーンアップしてください:

1. Claude Code プラグインのインストールを削除する。
2. リポジトリルートから ECC アンインストールコマンドを実行してインストール状態管理ファイルを削除する。
3. 手動でコピーした不要なルールフォルダを削除する。
4. 1つのパスだけを使用して一度だけ再インストールする。

## クロスプラットフォームサポート

このプラグインは **Windows、macOS、Linux** を完全にサポートし、主要な IDE（Cursor、Zed、OpenCode、Antigravity）および CLI ハーネスとの緊密な統合も備えています。すべてのフックとスクリプトは最大限の互換性を確保するため Node.js で書き直されています。

### パッケージマネージャーの検出

プラグインは以下の優先順位でお好みのパッケージマネージャー（npm、pnpm、yarn、または bun）を自動的に検出します:

1. **環境変数**: `CLAUDE_PACKAGE_MANAGER`
2. **プロジェクト設定**: `.claude/package-manager.json`
3. **package.json**: `packageManager` フィールド
4. **ロックファイル**: package-lock.json、yarn.lock、pnpm-lock.yaml、または bun.lockb からの検出
5. **グローバル設定**: `~/.claude/package-manager.json`
6. **フォールバック**: 最初に利用可能なパッケージマネージャー

お好みのパッケージマネージャーを設定するには:

```bash
# Via environment variable
export CLAUDE_PACKAGE_MANAGER=pnpm

# Via global config
node scripts/setup-package-manager.js --global pnpm

# Via project config
node scripts/setup-package-manager.js --project bun

# Detect current setting
node scripts/setup-package-manager.js --detect
```

または Claude Code の `/setup-pm` コマンドを使用してください。

### フックランタイムコントロール

ランタイムフラグを使用して厳格さを調整したり、特定のフックを一時的に無効にしたりできます:

```bash
# Hook strictness profile (default: standard)
export ECC_HOOK_PROFILE=standard

# Comma-separated hook IDs to disable
export ECC_DISABLED_HOOKS="pre:bash:tmux-reminder,post:edit:typecheck"

# Cap SessionStart additional context (default: 8000 chars)
export ECC_SESSION_START_MAX_CHARS=4000

# Disable SessionStart additional context entirely for low-context/local-model setups
export ECC_SESSION_START_CONTEXT=off

# Keep context/scope/loop warnings but suppress API-rate cost estimates
export ECC_CONTEXT_MONITOR_COST_WARNINGS=off
```

Windows PowerShell:

```powershell
[Environment]::SetEnvironmentVariable('ECC_CONTEXT_MONITOR_COST_WARNINGS', 'off', 'User')
```

- **パターン抽出** — コミット履歴から学習

### AgentShield — セキュリティ監査ツール

> Claude Code ハッカソン（Cerebral Valley x Anthropic、2026年2月）にて開発。1282件のテスト、98%のカバレッジ、102件の静的解析ルール。

Claude Code の設定を脆弱性、設定ミス、インジェクションリスクについてスキャンします。

```bash
# Quick scan (no install needed)
npx ecc-agentshield scan

# Auto-fix safe issues
npx ecc-agentshield scan --fix

# Deep analysis with three Opus 4.6 agents
npx ecc-agentshield scan --opus --stream

# Generate secure config from scratch
npx ecc-agentshield init
```

**スキャン対象:** CLAUDE.md、settings.json、MCP 設定、フック、エージェント定義、スキルの5カテゴリ — シークレット検出（14パターン）、パーミッション監査、フックインジェクション分析、MCP サーバーリスクプロファイリング、エージェント設定レビュー。

**`--opus` フラグ**は、レッドチーム／ブルーチーム／監査役のパイプラインで3つの Claude Opus 4.6 エージェントを実行します。攻撃側がエクスプロイトチェーンを発見し、防御側が保護策を評価し、監査役が両者の結果を優先度付きリスク評価としてまとめます。単なるパターンマッチングではなく、敵対的な推論を行います。

**出力形式:** ターミナル（A〜F のカラーグレード）、JSON（CI パイプライン）、Markdown、HTML。重大な検出結果があった場合、ビルドゲート用に終了コード 2 を返します。

Claude Code で `/security-scan` を実行するか、[GitHub Action](https://github.com/affaan-m/agentshield) を使って CI に組み込んでください。

[GitHub](https://github.com/affaan-m/agentshield) | [npm](https://www.npmjs.com/package/ecc-agentshield)

### Claude Code CLI バージョン

**最低バージョン: v2.1.0 以降**

このプラグインはプラグインシステムのフック処理に関する変更のため、Claude Code CLI v2.1.0 以降が必要です。

バージョンを確認するには:
```bash
claude --version
```

### 重要: フックの自動ロード動作

> 警告: **コントリビューターへ:** `.claude-plugin/plugin.json` に `"hooks"` フィールドを追加しないでください。これはリグレッションテストによって強制されています。

```
Duplicate hooks file detected: ./hooks/hooks.json resolves to already-loaded file
```

**経緯:** このリポジトリでは繰り返し修正と差し戻しのサイクルが発生していました（[#29](https://github.com/affaan-m/ECC/issues/29)、[#52](https://github.com/affaan-m/ECC/issues/52)、[#103](https://github.com/affaan-m/ECC/issues/103)）。Claude Code のバージョン間で動作が変わり、混乱を招いていました。現在はリグレッションテストにより、この問題が再導入されないよう防いでいます。

## インストール

### オプション 1: プラグインとしてインストール（推奨）

このリポジトリを使う最も簡単な方法 — Claude Code プラグインとしてインストールします。

```bash
# Add this repo as a marketplace
/plugin marketplace add https://github.com/affaan-m/ECC

# Install the plugin
/plugin install ecc@ecc
```

または `~/.claude/settings.json` に直接追加します。

```json
{
  "extraKnownMarketplaces": {
    "ecc": {
      "source": {
        "source": "github",
        "repo": "affaan-m/ECC"
      }
    }
  },
  "enabledPlugins": {
    "ecc@ecc": true
  }
}
```

これにより、すべてのコマンド、エージェント、スキル、フックに即座にアクセスできます。

> **注意:** Claude Code プラグインシステムはプラグイン経由での `rules` の配布をサポートしていません（[上流の制限事項](https://code.claude.com/docs/en/plugins-reference)）。ルールは手動でインストールする必要があります。
>
> ```bash
> # Clone the repo first
> git clone https://github.com/affaan-m/ECC.git
> cd ECC
>
> # Option A: User-level rules (applies to all projects)
> mkdir -p ~/.claude/rules/ecc
> cp -r rules/common ~/.claude/rules/ecc/
> cp -r rules/typescript ~/.claude/rules/ecc/   # pick your stack
> cp -r rules/python ~/.claude/rules/ecc/
> cp -r rules/golang ~/.claude/rules/ecc/
> cp -r rules/php ~/.claude/rules/ecc/
>
> # Option B: Project-level rules (applies to current project only)
> mkdir -p .claude/rules/ecc
> cp -r rules/common .claude/rules/ecc/
> cp -r rules/typescript .claude/rules/ecc/     # pick your stack
> ```

#### フックのインストール

リポジトリの `hooks/hooks.json` をそのまま `~/.claude/settings.json` や `~/.claude/hooks/hooks.json` にコピーしないでください。このファイルはプラグイン／リポジトリ向けであり、ECC インストーラー経由でインストールするか、プラグインとしてロードすることを想定しています。そのままコピーする方法はサポートされていません。

インストーラーを使用して Claude フックランタイムのみをインストールし、コマンドパスが正しく書き換えられるようにしてください。

```bash
# macOS / Linux
bash ./install.sh --target claude --modules hooks-runtime
```

```powershell
# Windows PowerShell
pwsh -File .\install.ps1 --target claude --modules hooks-runtime
```

これにより、解決済みのフックが `~/.claude/hooks/hooks.json` に書き込まれ、既存の `~/.claude/settings.json` はそのまま保持されます。

ECC を `/plugin install` でインストールした場合、それらのフックを `settings.json` にコピーしないでください。Claude Code v2.1 以降はプラグインの `hooks/hooks.json` を自動的にロードするため、`settings.json` に重複させると二重実行やクロスプラットフォームのフック競合が発生します。

Windows の注意事項: Claude の設定ディレクトリは `~/claude` ではなく `%USERPROFILE%\\.claude` です。

#### MCP の設定

Claude プラグインのインストールでは、ECC にバンドルされた MCP サーバー定義を意図的に自動有効化しません。これにより、厳格なサードパーティゲートウェイでのプラグイン MCP ツール名が長くなりすぎる問題を回避しつつ、手動での MCP セットアップも可能にしています。

ライブの Claude Code サーバー変更には、Claude Code の `/mcp` コマンドまたは CLI で管理する MCP セットアップを使用してください。Claude Code での無効化には `/mcp` を使用します。Claude Code はその選択を `~/.claude.json` に保持します。

リポジトリローカルの MCP アクセスには、`mcp-configs/mcp-servers.json` から必要な MCP サーバー定義をプロジェクトスコープの `.mcp.json` にコピーしてください。

ECC にバンドルされた MCP を独自に実行している場合は、以下を設定してください。

```bash
export ECC_DISABLED_MCPS="github,context7,exa,playwright,sequential-thinking,memory"
```

ECC が管理するインストールおよび Codex 同期フローは、重複を追加する代わりにそれらのバンドルサーバーをスキップまたは削除します。`ECC_DISABLED_MCPS` は ECC のインストール／同期フィルターであり、ライブの Claude Code トグルではありません。

**重要:** `YOUR_*_HERE` プレースホルダーを実際の API キーに置き換えてください。

## 主要コンセプト

### エージェント

サブエージェントは限定されたスコープで委譲タスクを処理します。例:

```markdown
---
name: code-reviewer
description: Reviews code for quality, security, and maintainability
tools: ["Read", "Grep", "Glob", "Bash"]
model: opus
---

You are a senior code reviewer...
```

### スキル

スキルは主要なワークフローサーフェスです。直接呼び出したり、自動的に提案したり、エージェントが再利用したりできます。ECC は移行期間中、メンテナンスされた `commands/` を引き続き提供していますが、廃止された短縮名シムは明示的なオプトイン用に `legacy-command-shims/` 配下に置かれています。新しいワークフロー開発は `skills/` を優先してください。

```markdown
# TDD Workflow

1. Define interfaces first
2. Write failing tests (RED)
3. Implement minimal code (GREEN)
4. Refactor (IMPROVE)
5. Verify 80%+ coverage
```

### フック

フックはツールイベントに応じて発火します。例 — `console.log` について警告する:

```json
{
  "matcher": "tool == \"Edit\" && tool_input.file_path matches \"\\\\.(ts|tsx|js|jsx)$\"",
  "hooks": [{
    "type": "command",
    "command": "#!/bin/bash\ngrep -n 'console\\.log' \"$file_path\" && echo '[Hook] Remove console.log' >&2"
  }]
}
```

### ルール

ルールは常に従うべきガイドラインであり、`common/`（言語非依存）と言語別ディレクトリに整理されています。

```
rules/
  common/          # Universal principles (always install)
  typescript/      # TS/JS specific patterns and tools
  python/          # Python specific patterns and tools
  golang/          # Go specific patterns and tools
  swift/           # Swift specific patterns and tools
  php/             # PHP specific patterns and tools
  arkts/           # HarmonyOS / ArkTS patterns and constraints
```

インストール方法と構造の詳細については [`rules/README.md`](rules/README.md) を参照してください。

## どのエージェントを使うべきか？

どこから始めればよいかわからない場合は、このクイックリファレンスを使用してください。スキルが正式なワークフローの窓口です。メンテナンスされているスラッシュエントリは、コマンドを起点とするワークフロー向けに引き続き利用できます。

| やりたいこと | 使用する窓口 | 使用されるエージェント |
|--------------|-----------------|------------|
| 新機能を計画する | `/ecc:plan "Add auth"` | planner |
| システムアーキテクチャを設計する | `/ecc:plan` + architect エージェント | architect |
| テストを先に書いてコードを書く | `tdd-workflow` スキル | tdd-guide |
| 書いたコードをレビューする | `/code-review` | code-reviewer |
| ビルドエラーを修正する | `/build-fix` | build-error-resolver |
| エンドツーエンドテストを実行する | `e2e-testing` スキル | e2e-runner |
| セキュリティ脆弱性を見つける | `/security-scan` | security-reviewer |
| デッドコードを削除する | `/refactor-clean` | refactor-cleaner |
| ドキュメントを更新する | `/update-docs` | doc-updater |
| Go のコードをレビューする | `/go-review` | go-reviewer |
| Python のコードをレビューする | `/python-review` | python-reviewer |
| F# のコードをレビューする | *(`fsharp-reviewer` を直接呼び出す)* | fsharp-reviewer |
| TypeScript/JavaScript のコードをレビューする | *(`typescript-reviewer` を直接呼び出す)* | typescript-reviewer |
| HarmonyOS アプリを開発する | *(`harmonyos-app-resolver` を直接呼び出す)* | harmonyos-app-resolver |
| データベースクエリを監査する | *(自動委譲)* | database-reviewer |
| 本番環境の ML 変更をレビューする | `mle-workflow` スキル + `mle-reviewer` エージェント | mle-reviewer |

### 一般的なワークフロー

以下では、メンテナンスされているコマンド窓口として残っている箇所にスラッシュ形式を示します。`/tdd` や `/eval` のような廃止済みの短縮名シムは `legacy-command-shims/` にあり、明示的なオプトインのみで利用できます。

**新機能の開始:**
```
/ecc:plan "Add user authentication with OAuth"
                                              → planner が実装ブループリントを作成
tdd-workflow skill                            → tdd-guide がテストを先に書くことを徹底
/code-review                                  → code-reviewer があなたの作業を確認
```

**バグの修正:**
```
tdd-workflow skill                            → tdd-guide: バグを再現する失敗テストを書く
                                              → 修正を実装し、テストが通ることを確認
/code-review                                  → code-reviewer: リグレッションを検出
```

**本番環境への準備:**
```
/security-scan                                → security-reviewer: OWASP Top 10 監査
e2e-testing skill                             → e2e-runner: 重要なユーザーフローのテスト
/test-coverage                                → カバレッジ 80%+ を確認
```

<summary><b>インストールされているエージェント/コマンドを確認するにはどうすればよいですか？</b></summary>

```bash
/plugin list ecc@ecc
```

プラグインから利用可能なすべてのエージェント、コマンド、スキルが表示されます。
</details>

<details>
<summary><b>フックが動作しない / "Duplicate hooks file" エラーが出る</b></summary>

これは最もよくある問題です。**`.claude-plugin/plugin.json` に `"hooks"` フィールドを追加しないでください。** Claude Code v2.1+ はインストール済みプラグインの `hooks/hooks.json` を自動的に読み込みます。明示的に宣言すると重複検出エラーが発生します。[#29](https://github.com/affaan-m/ECC/issues/29)、[#52](https://github.com/affaan-m/ECC/issues/52)、[#103](https://github.com/affaan-m/ECC/issues/103) を参照してください。
</details>

<details>
<summary><b>カスタム API エンドポイントやモデルゲートウェイ上の Claude Code で ECC を使用できますか？</b></summary>

はい。ECC は Anthropic ホスト型のトランスポート設定をハードコードしていません。ECC は Claude Code の通常の CLI/プラグイン窓口を通じてローカルで動作するため、以下の環境で動作します。

- Anthropic ホスト型 Claude Code
- `ANTHROPIC_BASE_URL` と `ANTHROPIC_AUTH_TOKEN` を使用した公式 Claude Code ゲートウェイ構成
- Claude Code が想定する Anthropic API を話す互換カスタムエンドポイント

最小構成の例:

```bash
export ANTHROPIC_BASE_URL=https://your-gateway.example.com
export ANTHROPIC_AUTH_TOKEN=your-token
claude
```

ゲートウェイがモデル名を再マッピングする場合は、ECC ではなく Claude Code 側で設定してください。ECC のフック、スキル、コマンド、ルールは、`claude` CLI が既に動作していれば、モデルプロバイダーに依存しません。

公式リファレンス:
- [Claude Code LLM gateway docs](https://docs.anthropic.com/en/docs/claude-code/llm-gateway)
- [Claude Code model configuration docs](https://docs.anthropic.com/en/docs/claude-code/model-config)

</details>

<details>
<summary><b>コンテキストウィンドウが縮小している / Claude がコンテキスト不足になっている</b></summary>

MCP サーバーが多すぎるとコンテキストを消費します。MCP ツールの各説明が 200k ウィンドウのトークンを消費し、最悪の場合 ~70k まで減少する可能性があります。SessionStart コンテキストはデフォルトで 8000 文字に制限されています。ローカルモデルや低コンテキスト構成では `ECC_SESSION_START_MAX_CHARS=4000` で制限を下げるか、`ECC_SESSION_START_CONTEXT=off` で無効化してください。

**解決策:** Claude Code の `/mcp` で未使用の MCP を無効にしてください。Claude Code はそれらのランタイム選択を `~/.claude.json` に書き込みます。`.claude/settings.json` と `.claude/settings.local.json` は、既にロード済みの MCP サーバーに対する信頼できるトグルではありません。

有効にする MCP は 10 個未満、アクティブなツールは 80 個未満に抑えてください。
</details>

<details>
<summary><b>一部のコンポーネントのみ（例：エージェントだけ）使用できますか？</b></summary>

はい。オプション 2（手動インストール）を使用して必要なものだけをコピーしてください:

```bash
# エージェントのみ
cp agents/*.md ~/.claude/agents/

# ルールのみ
mkdir -p ~/.claude/rules/ecc/
cp -r rules/common ~/.claude/rules/ecc/
```

各コンポーネントは完全に独立しています。
</details>

はい。ECC はクロスプラットフォームです:

- **非ネイティブハーネス**: Grok および類似インターフェース向けの手動フォールバックパス。[手動適応ガイド](docs/MANUAL-ADAPTATION-GUIDE.md)を参照してください。

## Cursor IDE サポート

ECC は Cursor の プロジェクトレイアウトに適応したフック、ルール、エージェント、スキル、コマンド、MCP 設定を含む Cursor IDE サポートを提供します。

### クイックスタート（Cursor）

```bash
# macOS/Linux
./install.sh --target cursor typescript
./install.sh --target cursor python golang swift php
```

```powershell
# Windows PowerShell
.\install.ps1 --target cursor typescript
.\install.ps1 --target cursor python golang swift php
```

### 含まれる内容

| コンポーネント | 数 | 詳細 |
|-----------|-------|---------|
| フックイベント | 15 | sessionStart、beforeShellExecution、afterFileEdit、beforeMCPExecution、beforeSubmitPrompt、およびその他 10 件 |
| フックスクリプト | 16 | 共有アダプター経由で `scripts/hooks/` に委譲する薄い Node.js スクリプト |
| ルール | 34 | 9 件の共通（alwaysApply）+ 25 件の言語固有（TypeScript、Python、Go、Swift、PHP） |
| エージェント | 48 | インストール時に `.cursor/agents/ecc-*.md` として配置。ユーザーやマーケットプレイスのエージェントとの衝突を避けるためプレフィックス付き |
| スキル | 共有 + バンドル | 翻訳済み追加分用の `.cursor/skills/` |
| コマンド | 共有 | インストール時の `.cursor/commands/` |
| MCP 設定 | 共有 | インストール時の `.cursor/mcp.json` |

### Cursor の読み込みに関する注意事項

ECC はルートの `AGENTS.md` を `.cursor/` にインストールしません。Cursor はネストされた `AGENTS.md` ファイルをディレクトリコンテキストとして扱うため、ECC のリポジトリ識別情報をホストプロジェクトにコピーするとそのプロジェクトが汚染されます。

Cursor のネイティブ読み込み動作は Cursor のビルドによって異なる場合があります。ECC はエージェントを `.cursor/agents/ecc-*.md` としてインストールします。お使いの Cursor ビルドがプロジェクトエージェントを公開しない場合、それらのファイルは隠れたグローバルプロンプトコンテキストではなく、明示的な参照定義として機能します。

### フックアーキテクチャ（DRY アダプターパターン）

Cursor は **Claude Code より多くのフックイベント**を持っています（20 対 8）。`.cursor/hooks/adapter.js` モジュールが Cursor の stdin JSON を Claude Code の形式に変換することで、既存の `scripts/hooks/*.js` を重複なく再利用できます。

```
Cursor stdin JSON → adapter.js → 変換 → scripts/hooks/*.js
                                              （Claude Code と共有）
```

主要なフック:
- **beforeShellExecution** — tmux 外での開発サーバーをブロック（exit 2）、git push レビュー
- **afterFileEdit** — 自動フォーマット + TypeScript チェック + console.log 警告
- **beforeSubmitPrompt** — プロンプト内のシークレット（sk-、ghp_、AKIA パターン）を検出
- **beforeTabFileRead** — Tab による .env、.key、.pem ファイルの読み取りをブロック（exit 2）
- **beforeMCPExecution / afterMCPExecution** — MCP 監査ログ

### ルールの形式

Cursor のルールは `description`、`globs`、`alwaysApply` を含む YAML フロントマターを使用します:

```yaml
---
description: "TypeScript coding style extending common rules"
globs: ["**/*.ts", "**/*.tsx", "**/*.js", "**/*.jsx"]
alwaysApply: false
---
```

## Codex macOS アプリ + CLI サポート

ECC は macOS アプリと CLI の両方に対して **一流の Codex サポート**を提供します。リファレンス設定、Codex 固有の AGENTS.md 補足、共有スキルが含まれています。

### クイックスタート（Codex アプリ + CLI）

```bash
# リポジトリで Codex CLI を実行 — AGENTS.md と .codex/ が自動検出される
codex

# 自動セットアップ: ECC アセット（AGENTS.md、スキル、MCP サーバー）を ~/.codex に同期
npm install && bash scripts/sync-ecc-to-codex.sh
# または: pnpm install && bash scripts/sync-ecc-to-codex.sh
# または: yarn install && bash scripts/sync-ecc-to-codex.sh
# または: bun install && bash scripts/sync-ecc-to-codex.sh

# または手動で: リファレンス設定をホームディレクトリにコピー
cp .codex/config.toml ~/.codex/config.toml
```

同期スクリプトは **追加のみ** の戦略を使用して、ECC の MCP サーバーを既存の `~/.codex/config.toml` に安全にマージします — 既存のサーバーを削除または変更することは一切ありません。`--dry-run` で変更のプレビューを確認できます。`--update-mcp` を使用すると ECC サーバーを最新の推奨設定に強制更新できます。

Context7 については、ECC は正式な Codex セクション名 `[mcp_servers.context7]` を使用しながらも、`@upstash/context7-mcp` パッケージを起動します。既存のレガシー `[mcp_servers.context7-mcp]` エントリがある場合、`--update-mcp` が正式なセクション名に移行します。

Codex macOS アプリ:
- このリポジトリをワークスペースとして開いてください。
- ルートの `AGENTS.md` が自動検出されます。
- `.codex/config.toml` と `.codex/agents/*.toml` はプロジェクトローカルに保持するのが最適です。
- リファレンスの `.codex/config.toml` は意図的に `model` や `model_provider` を固定しないため、上書きしない限り Codex は現在のデフォルトを使用します。
- オプション: グローバルデフォルト用に `.codex/config.toml` を `~/.codex/config.toml` にコピーできます。`.codex/agents/` もコピーしない限り、マルチエージェントのロールファイルはプロジェクトローカルに保持してください。

### 含まれる内容

| コンポーネント | 数 | 詳細 |
|-----------|-------|---------|
| 設定 | 1 | `.codex/config.toml` — トップレベルの承認/サンドボックス/web_search、MCP サーバー、通知、プロファイル |
| AGENTS.md | 2 | ルート（汎用）+ `.codex/AGENTS.md`（Codex 固有の補足） |


```bash
npm install ecc-universal
```

次に`opencode.json`に追加します：
```json

  "plugin": ["ecc-universal"]
```

- このリポジトリ内でOpenCodeを実行する、または
- バンドルされた`.opencode/`設定アセットをプロジェクトにコピーし、`opencode.json`内に`instructions`、`agent`、`command`エントリを設定する

## GitHub Copilot サポート

ECCはVS Code向けに**GitHub Copilotサポート**を提供しています。Copilot Chatのネイティブなインストラクションおよびプロンプトファイルシステムを利用するため、追加のツールは不要です。

### 含まれるもの

| コンポーネント | ファイル | 目的 |
|-----------|------|---------|
| コアインストラクション | `.github/copilot-instructions.md` | 常時読み込まれるルール：コーディングスタイル、セキュリティ、テスト、gitワークフロー |
| VS Code設定 | `.vscode/settings.json` | コード生成、テスト生成、レビュー、コミットメッセージ用のタスク別インストラクションファイル |
| 計画プロンプト | `.github/prompts/plan.prompt.md` | フェーズ別実装計画 |
| TDDプロンプト | `.github/prompts/tdd.prompt.md` | レッド・グリーン・改善サイクル |
| コードレビュープロンプト | `.github/prompts/code-review.prompt.md` | 品質とセキュリティレビュー |
| セキュリティレビュープロンプト | `.github/prompts/security-review.prompt.md` | OWASPに準拠した深いセキュリティ分析 |
| ビルド修正プロンプト | `.github/prompts/build-fix.prompt.md` | ビルドおよびCIエラーの体系的な解決 |
| リファクタリングプロンプト | `.github/prompts/refactor.prompt.md` | デッドコードの整理と簡素化 |

### クイックスタート（GitHub Copilot）

ファイルはすでに所定の場所にあります。このプロジェクトを含む任意のリポジトリを開くと、GitHub Copilot Chatが`.github/copilot-instructions.md`を自動的に読み込みます。
コミットされた`.vscode/settings.json`は`chat.promptFiles`を有効にし、VS Codeが`.github/prompts/`から再利用可能なプロンプトを読み込めるようにします。

Copilot Chatでワークフロープロンプトを使用するには：
1. VS CodeでCopilot Chatパネルを開く。
2. **ペーパークリップ / 添付**アイコンをクリックして**プロンプト...**を選択するか、`/`と入力してプロンプトを選択する。
3. プロンプトを選択する（例：`plan`、`tdd`、`code-review`）。

### 仕組み

VS CodeのGitHub Copilotは2種類のファイルを自動的に読み込みます：

- **`.github/copilot-instructions.md`** — リポジトリレベルのインストラクション。すべてのCopilot Chatリクエストに常時注入されます。ECCのコアコーディング標準、セキュリティチェックリスト、テスト要件、gitワークフローが含まれます。
- **`.github/prompts/*.prompt.md`** — ユーザーがオンデマンドで呼び出す再利用可能なプロンプトファイル。各プロンプトはCopilotを特定のECCワークフロー（計画→TDD→レビュー→リリース）に沿って導きます。

**`.vscode/settings.json`**はタスク別のインストラクションオーバーレイを追加し、コード生成、テスト記述、選択範囲のレビュー、コミットメッセージ作成のいずれを行っているかに応じて適切なコンテキストがCopilotに渡されます。

### 機能カバレッジ

| ECC機能 | Copilot相当 |
|-------------|-------------------|
| コーディング標準 | `copilot-instructions.md`経由で常時有効 |
| セキュリティチェックリスト | 常時有効 + `security-review`プロンプト |
| テスト / TDD | 常時有効 + `tdd`プロンプト |
| 実装計画 | `plan`プロンプト |
| コードレビュー | `code-review`プロンプト |
| ビルドエラー解決 | `build-fix`プロンプト |
| リファクタリング | `refactor`プロンプト |
| コミットメッセージ形式 | `settings.json`のタスク別インストラクション |
| フック / 自動化 | 非対応（Copilotにはフックシステムがない） |
| エージェント / 委任 | 非対応（CopilotにはサブエージェントAPIがない） |

### 制限事項

GitHub CopilotにはフックシステムもサブエージェントAPIも存在しないため、ECCのフック自動化（自動フォーマット、TypeScriptチェック、セッション永続化、開発サーバーガード）とエージェント委任は利用できません。インストラクションおよびプロンプト層は、ECCのコーディング哲学（標準、セキュリティ、TDD、ワークフロー）をすべてのCopilot Chatセッションに反映させます。

## トークン最適化

トークン消費を管理しないと、Claude Codeのコストが高くなります。これらの設定は品質を損なうことなくコストを大幅に削減します。

### 推奨設定

`~/.claude/settings.json`に追加してください：

```json
{
  "model": "sonnet",
  "env": {
    "MAX_THINKING_TOKENS": "10000",
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50"
  }
}
```

| 設定 | デフォルト | 推奨値 | 効果 |
|---------|---------|-------------|--------|
| `model` | opus | **sonnet** | 約60%のコスト削減；コーディングタスクの80%以上に対応 |
| `MAX_THINKING_TOKENS` | 31,999 | **10,000** | リクエストごとの隠れた思考コストを約70%削減 |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | 95 | **50** | より早期に圧縮——長いセッションでより高い品質 |
| `ECC_CONTEXT_MONITOR_COST_WARNINGS` | on | **サブスクリプションユーザーはoff** | エージェント向けのAPIレート推定警告を抑制し、コンテキスト/スコープ/ループ警告は維持 |

深いアーキテクチャ的推論が必要な場合のみOpusに切り替えてください：
```
/model opus
```

### 日常ワークフローコマンド

| コマンド | 使用タイミング |
|---------|-------------|
| `/model sonnet` | ほとんどのタスクのデフォルト |
| `/model opus` | 複雑なアーキテクチャ、デバッグ、深い推論 |
| `/clear` | 関連のないタスク間（無料、即時リセット） |
| `/compact` | 論理的なタスクの区切りで（調査完了、マイルストーン達成） |
| `/cost` | セッション中のトークン消費の監視 |

Claudeサブスクリプションを使用しており、コンテキストモニターのAPIレート推定が不要な場合は、`ECC_CONTEXT_MONITOR_COST_WARNINGS=off`を設定してください。これはエージェント向けのコスト警告のみを抑制し、コンテキスト枯渇、スコープ、ループの警告は無効になりません。

### 戦略的コンパクション

`strategic-compact`スキル（このプラグインに含まれています）は、95%コンテキスト時の自動コンパクションに頼るのではなく、論理的な区切りで`/compact`を提案します。完全な判断ガイドについては`skills/strategic-compact/SKILL.md`を参照してください。

**コンパクションを行うべきタイミング：**
- 調査・探索後、実装開始前
- マイルストーン達成後、次のタスク開始前
- デバッグ後、機能開発再開前
- アプローチが失敗した後、新しいアプローチを試みる前

**コンパクションを行うべきでないタイミング：**
- 実装の途中（変数名、ファイルパス、部分的な状態が失われます）

### コンテキストウィンドウ管理

**重要：** すべてのMCPを同時に有効にしないでください。各MCPのツール説明が200kウィンドウからトークンを消費し、最悪の場合約70kまで削減されることがあります。

- プロジェクトごとに有効なMCPを10個以内に抑える
- アクティブなツールを80個以内に抑える
- `/mcp`を使用して未使用のClaude Code MCPサーバーを無効にする（ランタイム上の選択は`~/.claude.json`に保持されます）
- `ECC_DISABLED_MCPS`はインストール/同期フロー中にECC生成のMCP設定をフィルタリングする場合にのみ使用する

### エージェントチームのコスト警告

エージェントチームは複数のコンテキストウィンドウを生成します。各チームメンバーは独立してトークンを消費します。並列処理が明確な価値をもたらすタスク（マルチモジュール作業、並列レビュー）にのみ使用してください。単純な逐次タスクにはサブエージェントのほうがトークン効率が高いです。
